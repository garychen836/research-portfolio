Dep Twin: an AI agent that plans experiments, with a human approving every real run

The research question

Developing a new recipe on a semiconductor deposition tool means running many expensive test wafers, and each real run costs time and money. At Applied Materials I used algorithmic design of experiments (DOE) to cut that cost. I wanted to know whether an AI agent working on a physics-based digital twin could reach the same answer with far fewer real runs, without losing the rigor and traceability that engineers need.

What I built

  • A digital twin of an atomic layer deposition (ALD) tool. Every physical parameter cites a public source (DOI and table or page), and any parameter without one is marked "to verify" for review. No employer data was used.
  • A Bayesian-optimization agent that proposes the next recipe. A validator checks each proposal for units, safety interlocks, duplicates and confidential text. Every prediction comes with a mean, a standard deviation and a 95% interval.
  • Agents propose and humans approve. Only a human with an approval token can run a proposal on the "real" tool, which is a hidden model the agent never sees. There is deliberately no approve tool in the MCP toolbox.
  • An MCP toolbox so other AI agents can simulate, propose and explain, plus a web page with run history, a best-so-far plot, wafer maps and a what-if panel.
  • Evaluation infrastructure: a red-team suite, sanity checks before every deploy, an append-only record of every run (inputs, model version, seed, who approved it), and a lessons log.

Results, tested on 20 hidden "real" tools

18 runsmedian for the agent to reach the best result of an 81-run full-factorial DOE (success threshold: ≤ 27)
4 runsmedian for the twin-warm-started agent to match the best result of a 27-run central composite design
93%share of real outcomes that fell inside the agent's own 95% prediction interval, after calibration

I set the success criterion and the evaluation protocol before looking at results, and nothing was tuned afterwards. The report also says where it failed: on 6 of 20 tools the plain agent never reached the DOE's best result. The phase-2 goal of predicting how a hardware part swap changes the process missed its 0.3-point accuracy target, and the report says so.

Why it matters for AIRS: the questions are the same as for AI research tools. When should the AI act, and when should a person approve? How do you show uncertainty and sources so people can trust an output? And how do you evaluate the system honestly before anyone relies on it?

Mika MBA Companion: one agent for every recruiting path

The research question

MBA students on paths with no formal recruiting (venture, startups, climate, niche industries) piece together roles, events and deadlines from more than 15 separate pages. Where does that time go, and which information do they actually act on?

What I built

  • A data pipeline that pulls public listings from 15+ sources into one schema: 700+ roles and 100+ events a week. It works offline from a snapshot, so anyone can rebuild it.
  • Classification with code first and AI second. Rules assign each role a job family. The few roles the rules can't place go to the model in a single batch, and the result is cached for everyone, so cost doesn't grow with the number of users.
  • An assistant that proposes and lets the user decide. Every change the agent suggests appears as a button with Undo. The agent never edits a student's data on its own.
  • Instrumentation: token use by purpose, a service log, and a plain-text morning report (visitors, what they did, tokens and dollars). It's my own research archive of how the tool is used.

How it differs from Career Compass: Mika is a personal agent for one cohort's whole MBA life. It knows each student's paths, courses and contacts, and it acts on their behalf (with their OK). Career Compass, below, is an open job feed for any student, built around where each listing comes from.

What this shows for AIRS: combining many messy sources into one view, keeping the person in control, and measuring use from day one. Research repositories need the same three things.

Yale Career Compass: entry-level jobs from employers' own career pages

The user need

Students, especially international students, waste hours on job boards full of reposted, stale and duplicate listings, and they still can't tell which employers have sponsored visas before. I wanted every listing to be real, current and traceable to its source.

What I built

  • A daily pipeline that reads 2,700+ internships, co-ops and new-grad roles straight from employers' own hiring systems (Greenhouse, Lever, Ashby, Workday). It uses no job boards or aggregators, and every card links to the original posting.
  • Public data joined in: each employer is tagged with its H-1B filing history from U.S. Department of Labor records. The page labels this as a history, not a promise of sponsorship, and treats "no record" as unknown.
  • An "Ask Mika" chat that can't invent results. Code answers most questions from the site's own data, and the model only interprets the question. The server drops any role the model mentions that the code didn't find, and a newly discovered role joins the shared pool only after code re-reads it on the company's page.
  • Privacy and cost limits by design: no accounts, saved roles and applications stay in the browser, statistics are aggregate counts only, and paid model steps stop at a small daily dollar cap.
  • A 40-attack red team (hostile postings, prompt injection, privacy checks) runs offline on every push.

How it differs from Mika: Compass is open to any student, not just one MBA program, and it covers internships, co-ops and new-grad jobs only. It needs no account or profile. Its focus is trust: original postings, visa history and nothing invented.

What this shows for AIRS: an insight tool is only as good as the provenance of its data. Each answer here can be traced to a source, and the AI is kept to interpreting questions so it can't make results up.

Sales Desk: an AI desk for prospect research and quoting

The problem

Salespeople spent hours researching each prospect company, rebuilding quotes from inquiry emails and drafting follow-ups. I started by mapping that workflow, then automated the steps that took the most time.

What I built

  • A research agent that profiles a company with a fixed budget of 4 searches and 6 page reads, stays on that company's domain, cites every source, caches results for 60 days, and treats web pages as data, never as instructions.
  • A "Today" page built from data: each card is one piece of pending work (an unanswered inquiry, a quote that's due) with exactly one main action, and the card disappears once the work is done. A new user gets from the first card to a finished quote in 5 clicks.
  • Plain language throughout. An automated test checks every page for developer jargon.
Guardrails: the AI chooses among options but never invents a number. Every price and amount comes from code and the price book, and a checker flags any amount in a draft email that doesn't match the quote. Nothing is sent automatically. Build reports separate what passed with real data from what passed only in a mock environment.

Also built

  • Mika Fab Academy (live): a 3D digital twin of a chip fab for training new engineers. I designed it after interviewing working-level engineers, and its AI quiz writer may only use audited facts.

VoltCart: would food trucks rent swappable batteries?

Plan

The hypothesis came from an earlier market assessment: food-truck generators are noisy, smell of fuel and cost $300+ a month. A battery would fix that, but the upfront cost is a barrier. We wrote down hypotheses and pass/fail thresholds before the first interview, for example "most trucks need 1 module a day; pass if ≥ 70% log ≤ 6 kWh per service day."

Recruit

GroupnWhy they're in the sample
Food-truck owners who run gas generators15Core user; screened out anyone without a generator
Landscaping companies5Adjacent use case; towns are banning gas leaf blowers
Commissary operators3Would host the charging cabinet
Event organizers3Decide which vendors are allowed
Fire marshal1Approves (or blocks) the charging site

Collect: interview rules I wrote for the team

  • Ask what they did, not what they would do: "What did you spend on gas last month?", not "Would a battery save you money?"
  • Don't pitch until the offer section. Ask for proof (receipts, generator model, photos). Write down exact quotes, and record only with permission.
  • Pricing uses the four Van Westendorp questions before revealing the real price, then compares it with what they said they spend on gas.
  • End every interview with "Who else should we talk to?"
The protocol is built to avoid the biggest risk in discovery interviews, which is hearing "sounds great" from people who will never pay. Each hypothesis is tied to a behavior or artifact we can check.

Status: interviews are running through December 2026. Findings and the pass/fail result for each hypothesis will be added once they are synthesized.

What actually breaks for energy-storage users

I organized the field feedback by use case (home vs. commercial and industrial) and size (2–10 kWh vs. over 10 kWh). For each of the four segments I recorded concrete failure stories, then turned them into the minimum a product must meet.

SegmentMost-cited painMinimum bar
Home, smallApps that require the cloud stop working during an outage, which is exactly when the battery is neededFull control without a network; high surge power for fridges and pumps
Home, largeBattery can't talk to third-party inverters; won't charge below 0 °COpen protocols; built-in self-heating
Commercial, smallAfter a deep discharge, the battery locks up and a technician has to drive out to restart itWakes up by itself on solar or grid power; zero site visits
Commercial, largeMissing UL 9540A certification keeps systems off sites; cooling fails more often than the batteriesComplete safety certifications; reliable cooling; local spare parts
Key finding: in every segment, people care less about features than about the product working when no one is around, during an outage, in the cold or at a remote site.

Battery packs: where not to compete

Quantitative: list vs. street price, $/kWh

Consumer brandList → typical discounted price

Qualitative: what the shelves and the job sites showed

  • Packs made in 2024 were still sitting unopened at camping and hardware stores, and one big-box store kept the category more than 50% off. The consumer market is saturated, and its software ecosystems are a strength we couldn't match.
  • Small contractors in Seattle didn't ask for battery packs at all, and that held up at a Texas trade show. The real competitor is the gas generator, not another battery brand.
  • An unexpected signal: small construction crews from Mexico, Honduras and Colombia were the most interested, and they were also the most price-sensitive.
Recommendation: don't enter the consumer market; focus on industrial uses and Latin America. The food-truck finding (a market still wide open, where generator noise and fuel smell are the pain) carried into the VoltCart study.
Instrument design
Context
Requirements for an airport ground-equipment startup's battery modules, Nov 2026
Format
Spreadsheet survey in two tiers: 20 core items and 36 optional technical items

A questionnaire people actually finish

  • Respect the respondent's time. The core tab takes 10–15 minutes and the technical tab is optional. Every item has an example answer.
  • "Not sure" is a perfectly good answer. Respondents don't make up specs just to fill a cell.
  • Make them rank trade-offs. "If targets conflict, rank weight, energy, cost, cycle life, size" shows real priorities that separate questions would hide.
  • Ask about context, not just specs. Swap frequency, shift patterns and climate at the actual airports let us work out requirements the customer didn't know to state.
  • Each question says why it's being asked (for example, "helps us size connector and latch life"), and the survey asks for supporting files such as photos and existing datasheets.

Also

  • Field-research planning: I screened 30+ industry events by research question and audience (end users, dealers, decision-makers) and ranked a top five, to decide where to observe buyers and recruit interviewees.

Publications: fuel cell research at Cornell

As a graduate researcher at Cornell, I co-authored two peer-reviewed papers on catalysts for alkaline fuel cells. The goal was to replace expensive platinum with cheaper materials. Both studies screened many candidates systematically rather than testing one at a time, which is where I learned to design studies carefully and report only what the data supports.

Proceedings of the National Academy of Sciences · 2019

Octahedral Spinel Electrocatalysts for Alkaline Fuel Cells

A systematic study of 15 spinel-oxide nanoparticles with controlled shapes. The best one matched platinum's activity for the key fuel-cell reaction, using only cheap, abundant metals.

Yao Yang, Yin Xiong, Megan E. Holtz, Xinran Feng, Rui Zeng, Gary Chen, Francis J. DiSalvo, David A. Muller, Héctor D. Abruña
